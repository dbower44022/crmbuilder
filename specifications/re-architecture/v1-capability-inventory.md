## Purpose

Version 1 of CRMBuilder is still on disk and version 2 still imports from it. Before any of version 1 is absorbed into a version 2 segment or deleted, every version 1 capability is classified here as **absorb**, **drop** or **already covered**, with the evidence read for that classification and, where absorbed, the version 2 segment that will own it.

This document is a reading task and a work order. It moves no code, deletes no code, and creates no capability. Each absorbed capability becomes its own planning item under its own requirement after the product owner approves the area it sits in.

Approval is area by area. An area is approved when every row in it carries a disposition that is not marked inferred.

## Method

A capability is something a person gets, not a function that exists. "Creates a missing field on the target system" is a capability; `FieldManager._create()` is not. One capability may span several functions, and one module may hold several capabilities.

A disposition is derived from reading both code bases, never from a module or symbol name that looks similar to another. For each capability the version 2 code that would cover it was located and read far enough to say whether the behaviour is equivalent, partial or absent. Partial coverage names what is missing. Where reading did not settle the question, the row says unsettled and gives the reason; an area cannot be approved while it holds an unsettled row.

The version 2 segments are the seven approved in DEC-1077 and recorded in `record-type-segment-map.md`: Client Management; Discovery and Requirements; Solution Design; Build; Operate; CRMBuilder Delivery; Shared Core. Applying a definition to a live CRM system is Build. Provisioning, upgrading and recovering a server is Operate.

### Three further things that gate deletion, which the planning item's list does not name

1. **The version 2 test suite imports version 1 directly** — `ConfigLoader`, the deployable layout types, the deploy outcome type, the instance role, the settings results, the import manager, and the version 1 audit capture modules, across roughly a dozen test files. Five of those symbols appear *only* in tests, so they are not capability rows, but they hold `espo_impl/core/reconcile/` and `import_manager.py` alive.
2. **The publish path drags the graphical toolkit into a headless process.** `get_espo_entity_name` lives in a dialog module that imports the widget library at module level, so running a publish in the web service loads the whole user-interface toolkit. This is a live consequence, not untidiness.
3. **Only three imports can be removed on their own today.** Substituting version 2's own entity-name function; dropping the role argument, which is already the default; and, once those two go, nothing else — the profile class cannot be rerouted until a write-capable client exists, because the version 1 client's constructor takes it.

**Area 0**: 25 symbols. Three already covered, 22 absorb, none dropped. The absorb set is the apply engine itself — the live-system client with its seventeen write methods, the pipeline, the field manager, the settings writer, the declaration parser and validator, and the five server-provisioning phases.

## Area 1 — configuration engine deployment managers

### The finding that governs this area

**Version 2 has no apply engine of its own.** `publish/service.py:publish` builds a version 1 `EspoAdminClient` and calls version 1's `deploy_pipeline`, whose `DeployManagers` defaults to the version 1 entity, field, layout, relationship, entity-settings and message-template managers. Version 2's own instance client, `introspect/espo_client.py`, exposes read methods only — `get_all_scopes`, `get_entity_field_list`, `get_layout`, `get_client_defs` — and no create, update or save method at all.

So for the direction that writes to a live CRM system, version 2's coverage is *no* almost everywhere: version 2 depends on these modules rather than reimplementing them. Version 2's genuine contribution in the same territory is the other two directions — generating the declaration (`adapters/espocrm/`) and reading the live system back for drift (`introspect/reconcile.py`).

This is why area 1 is almost entirely **absorb**, and why it is large: absorbing it means building the apply engine version 2 has never had.
